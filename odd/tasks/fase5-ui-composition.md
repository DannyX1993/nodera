## Non-goals

- SDK package surface (@nodera/sdk stays untouched) and Plugin API/manifest/lifecycle (Phases 6-7). UI packages expose their own public entry points, designed to become SDK surface later.
- Accessibility & Internationalization modules (PRODUCT-DESCRIPTION §3.22 = Phase 8): no shortcut layer, no i18n catalog, no RTL layout in this phase. Basic a11y hygiene (roles/labels/keyboard escape for menus) is included because menu/dialog roles are part of correct UI behavior.
- Any execution/runtime of nodes or tools; any document/GGD contract change; any Vue/Angular adapter.
- Any `@xyflow/react` import outside `packages/canvas-react-flow`.
- Any layout chosen, imposed or defaulted by the framework on the host app.

## Decisions

- D1 (amendment): layout *model types* (`PanelRegion`, `Rect`, `PanelState`, `LayoutState`, `LayoutDefinition`) live in `ui-core` so both the store and the layout engine share them without a cycle; `LayoutRegistry` and the layout computations live in `layout-engine`.
- D1: Package split (presentation layer only, no domain/application logic):
  - `@nodera/ui-core` — framework-agnostic UI contracts and state: panel definitions, tool/command descriptors, `PanelRegistry`/`ToolRegistry`, the UI state store, panel/layout/menu state types. No React, no DOM, no React Flow.
  - `@nodera/theme-engine` — design tokens, theme definitions, `ThemeRegistry`, default theme, pure `themeToCssVariables`.
  - `@nodera/layout-engine` — layout definitions, `LayoutRegistry`, predefined layouts, pure layout reducers (resize/hide/dock/float) and `resolveLayout` geometry, versioned layout persistence port + in-memory store.
  - `@nodera/ui-react` — all 16 components, React providers, hooks, component-replacement registries (panel/property/toolbar renderers), JSX styling. Depends on ui-core, theme-engine, layout-engine, application, domain, graph-model, node-registry, edge-registry, property-system, validation, history, contracts.
  - Dependency direction: theme-engine → contracts; ui-core → contracts; layout-engine → ui-core + contracts; ui-react → all above. No cycles.
- D2: Styling without a new build pipeline. `build` is `tsc --noEmit` repo-wide and no CSS/asset pipeline exists; themes are data (`DesignTokens`) plus a pure `themeToCssVariables(theme): Record<string,string>` map. `ThemeProvider` (ui-react) writes those entries as CSS custom properties on a wrapper element via `style`; components style themselves inline with `var(--ndr-*, fallback)` so nothing requires a stylesheet. Hosts can override any token with their own CSS because the contract is CSS variables (S3 "CSS Variables").
- D3: UI state lives in one framework-agnostic `UiStateStore` (ui-core) with immutable snapshots + `subscribe`; React binds it through `useSyncExternalStore` (no state library; the repo has none today). The store holds theme id, layout state/preferences, panel visibility, open menus/context menu target, search query. Editor state (selection, history, clipboard) stays in `application`; canvas state (zoom/pan/viewport) stays in the React Flow adapter. Documented rationale for the FASE5 ambiguity (panel state under editor state, visibility under UI state): all *presentation* state is unified in the UI store and never persisted into the document, which satisfies both S5 sentences.
- D4: Toolbar/palette/context-menu actions are declarative tool descriptors (`ToolDefinition.command` union: `undo`, `redo`, `delete-selection`, `copy-selection`, `cut-selection`, `paste-selection`, `validate`, `fit-view`, `add-node`, `toggle-panel`, `dock-panel`, `custom`), stored in a `ToolRegistry` (ui-core) and executed by ui-react's command hook against application use cases. No functions inside registries or serializable data; hosts extend through `custom` commands + `onCommand`.
- D5: One additive application event: `selection.changed` with `{selectedNodes: readonly string[]; selectedEdges: readonly string[]}` emitted by `selectNode`, `selectEdge`, `selectMultiple`, `clearSelection`. Phase 4 documented the gap (edge selection/deselection emit nothing) and panels cannot re-render without it. The 16 existing event names, payloads and emitters are unchanged (existing tests must pass untouched); this appends a name, it does not alter a contract others consume.
- D6: `MinimapPanel` is a plain SVG overview of graph positions + selection rendered by ui-react (no `@xyflow/react` import), so UI composition never couples ui-react to React Flow. The React Flow `MiniMap` remains available inside the adapter through `GraphCanvas.showMinimap` (Phase 4, S6 keeps it in the adapter).
- D7: Palette → canvas drop is added additively in the adapter: `GraphCanvas.onDropNodeDefinition?(definitionId, position)` computed with React Flow's `screenToFlowPosition`; the palette writes a stable MIME payload `application/nodera-node-definition`. Palette click adds at a host-independent offset instead.
- D8: `PortRendererRegistry` (adapter, replaces PortVisual.renderer gap from phase 4) plus token fallbacks (`var(--ndr-node-*)`, `var(--ndr-edge-*)`) in the default renderers, so S3's Handle/Node/Edge/Selection styles are real without a stylesheet.
- D9: Layout geometry is computed by pure functions (`resolveLayout`) over region sizes; `EditorShell` renders the resolved layout and hosts optional splitters. It imposes nothing: regions are optional, only the canvas region is required, and a host may skip `EditorShell` entirely and place components itself (S2). Dockable = moving a panel between regions; floating = region `floating` + rect; hideable = `visible:false` with size kept.
- D10: Layout preferences persist through a `LayoutPreferenceStore` port in layout-engine (`load()/save()`), with an in-memory implementation and versioned, validated serialization. The empty `adapter-storage-*` packages are Phase 8 infra and stay untouched; hosts pass their own store.
- D11: `PropertiesPanel` is fully driven by `PropertyDefinition` + property-system evaluators (visibility, enabled, effective options, value validation) with replaceable per-type renderers; `InspectorPanel` is the read-only structural view (ids, definition version, ports, raw properties/metadata). No rigid per-node-type inspector (S7).
- D12: New packages get the same conventions as `canvas-react-flow`: `"type":"module"`, `main`/`types` → `./src/index.ts`, kebab-case files, colocated `*.test.ts(x)`, per-package `vitest.config.ts`, `tsc --noEmit` build. ui-react uses jsdom + `@testing-library/react` with its own `src/test/setup.ts` (React 19 + `IS_REACT_ACT_ENVIRONMENT`), reusing the phase-4 polyfill pattern only where needed.
- D14 (resolved during T8): `json-editor` keeps the phase-1 contract — its value is the *serialized JSON string* (`property-system/src/property-type.ts` classifies it string-like and documents "a `json-editor` still holds a serialized string"). The renderer therefore commits the raw text only when it parses, reports invalid JSON inline as a local issue and never persists an unparseable draft; `object`/`array` properties commit parsed structures, which the core accepts. Core validation semantics are unchanged.
- D13 (amended during T12): the repository has no ADR mechanism (`docs/adr/` does not exist), so Phase 5 decisions are recorded here plus a package-boundary section in `docs/PROJECT-STRUCTURE.md` §7.2 instead of an ADR.
- D13 (original): `examples/phase5-demo` is the runnable host proving composition: two different layouts from the same core (classic editor layout and canvas-only layout), theme switch, component replacement, palette/properties/validation panels. Docs updated: package READMEs, `docs/PROJECT-STRUCTURE.md`, `docs/ROADMAP.md` check-off note, ADR `docs/adr/0005-phase5-ui-composition.md`.
