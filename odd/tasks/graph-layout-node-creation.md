# feature: graph-layout-node-creation

Graph layout modes (free vs auto, horizontal vs vertical) plus a configurable node-creation dialog for the "+" action.
Branch: `feature/graph-layout-node-creation` (off master). Three chained work units: placement config, layout port, dialog.

## Specs

- S1: (user, verbatim) "Estaría bien en el SDK tener algo para poder elegir si queremos que el grafo sea libre o dynamic layout, dando a elegir tambien si horizontal o vertical (parecido al ejemplo de https://reactflow.dev/examples/layout/dynamic-layouting)." The example is orientative only; no part of it may be copied in a way that breaks engine/framework agnosticism (L2).
- S2: (user, verbatim) "Para ello, si se necesita tambien poder hacer modales, completamente configurables y personalizables, para que al darle al boton de "+" puedas elegir que nodo añadir."
- S3: (user, verbatim) "lo del dynamic layout va dentro del canvas por lo que debe ir en ui-core y ui-react (igual que con la modal)" — resolved by S5: the *trigger*, the editor-side controls and the dialog belong to ui-core/ui-react; the geometry and the position writes do not.
- S4: (user decisions, L3, verbatim option labels) "Las tres, en fases encadenadas" (T1 -> T2 -> T3, one reviewable work unit each); "Solo nodos sin posición + Arrange manual" (automatic layout never moves a node the host or the user already positioned; re-laying out the whole graph is an explicit `Arrange` action); "Solo configuración del host" (no runtime toggles, no framework-invented defaults: the host declares the mode).
- S5: Layer contract (architecture decision, L4; evidence in that entry). Node positions are **document** data (`packages/graph-model/src/node.ts:29`), rendered from the document (`packages/react-flow/src/map/react-flow-mapper.ts:155`); canvas state is viewport/zoom/pan only (`packages/ui-core/src/ui-state.ts:26-28`). Therefore: (a) geometry is computed by a framework-agnostic module with no React/React Flow/`@xyara` import (AGENTS.md §4.1, §4.2, §7); (b) position writes go through `@nodera/application` use cases so each is one reversible history unit (AGENTS.md §12); (c) never write graph positions from a ui-react effect or from React Flow state; (d) tests for the geometry run without React (AGENTS.md §14).
- S6: (AGENTS.md §3, verbatim) "No actualices dependencias por iniciativa propia ni introduzcas una librería para resolver algo que pueda resolverse con las abstracciones existentes, salvo que exista una justificación técnica clara." An automatic layered strategy may depend on `@dagrejs/dagre` behind the port only after the dependency decision is recorded (L5). T1 must ship with no new dependency.
- S7: (AGENTS.md §14/§17) every behavior change pins tests through the public interface, and the docs describing the changed configuration are updated in the same work unit.
- S8: (AGENTS.md §13) invalid host configuration never silently produces geometry: it yields a structured diagnostic and fails closed (the graph keeps today's behavior).
- S9: (decision, L7) No external layout dependency in this feature. The layered placement is implemented in-house behind the strategy port: the scope the host chose (automatic placement only for unpositioned nodes, re-layout only through an explicit `Arrange`) does not need crossing minimization to be useful, and `dagre`'s own caveats (input-order dependence, super-linear cost, recursive DFS, module-level state before 3.1.3) would still leave us with the same obligations — sort by id, set a size threshold, build a degradation path. A dependency that does not remove the engineering we own is not the "justificación técnica clara" AGENTS.md §3 asks for. It becomes justified the day a stated quality bar exists (crossing minimization, edge bend points, large graphs): then an adapter pins `>= 3.1.3` behind the same port.
- S10: `Arrange` semantics (T2). Rank every node by longest path from the source nodes (nodes with no incoming edge); a component made only of cycles is placed after the resolved ranks, ordered by node id, so the result stays deterministic. Within a rank, order by node id — no crossing minimization, no edge bend points (stated limitation, not an oversight). `horizontal` puts the rank on `x` (`rankSpacing`) and the in-rank order on `y` (`nodeSpacing`); `vertical` swaps the axes. `Arrange` repositions **every** node of the graph as one history unit, all-or-nothing: if any position cannot be applied, nothing moves. It is requested explicitly, never triggered by an add, an edge change or a read.
- S11: The strategy port is framework-agnostic and React-free (S5), takes plain data (instance ids, current positions, edges, options) and answers either one position per node or a structured diagnostic; the host picks the strategy in configuration.
- S12: (user, L9) The in-house implementation ships as the initial approach, but a third-party strategy (`@dagrejs/dagre` or any other) must be easy to add later and **selectable**: strategies live in a registry (`LayoutStrategyRegistry`, same conflict rules as every other registry: a used id is a `duplicate-id` error, an unknown one is `not-found`), the host registers its own adapter and selects it by id in `graph.layout.strategy`, and the selected id is the only thing carried downstream. The framework ships no external dependency (S9); the adapter's dependency belongs to the host's build. The registry never keeps a default it no longer holds: unregistering the selected strategy moves the selection to the first remaining one.

- S14: Dialog contract (T3). A dialog is declarative **data** in `ui-core`, never a React component: `DialogDefinition` (qualified id, title, optional description, size, `dismissible`, optional metadata) registered in a `DialogRegistry` with the same duplicate-id/not-found rules as every other registry, and the open dialog tracked in the existing `UiState` as one optional id. `ui-core` stays free of React, DOM and dialog implementation details; the renderer binds the definition in `ui-react` (AGENTS.md §4.5, §7).
- S15: The `ui-react` dialog primitive is accessible by construction (AGENTS.md §15): `role="dialog"`, `aria-modal`, an accessible name from the definition title, focus moved inside when it opens, focus trapped while it is open, focus returned to the trigger when it closes, `Escape` and backdrop click only when the definition is `dismissible`, and every control reachable by keyboard. The node-creation dialog renders the node definitions the host registered (the palette vocabulary) and dispatches the existing `{ kind: "add-node", definitionId }` command, so it is a composition of the registry and the command bus, not a second creation path.
- S16: (user, L13) A second example (`examples/layout-switch-demo`) shows a host switching the graph layout: So a host can switch direction or spacing without rebuilding the builder, `builder.graph.arrange(options?)` accepts per-call overrides of `direction`, `spacing` and `rankSpacing` that win over the builder configuration for that one explicit action and change nothing persisted. The switching still belongs to the host's own UI: no editor toggle is added. it selects the strategy (`free`/`layered`), the direction (`horizontal`/`vertical`), runs `Arrange`, and opens the node-creation dialog from a "+" button. The switching lives in the **host's own** UI calling `builder.graphLayout.setDefault` and `builder.graph.arrange()`; the framework still ships no runtime toggle for the editor (S4).
- S17: (user, L13) Complete package documentation: `packages/graph-layout/README.md` documents every export (port types, both built-in strategies, the registry and its rules), the exact placement rules with their defaults, the stated limitations, and the steps plus a host-side sketch for adding a third-party adapter; `docs/GRAPH-LAYOUT.md` is the page that ties the model to the SDK surface and the example, and the repository index documents that point to it.

- S13: `Arrange` wiring (T2c). The application layer gains **one** use case that applies N node positions as a single history unit, all-or-nothing: every node id and every position is validated before anything is written, and a failure writes nothing, pushes nothing and emits nothing (AGENTS.md §12, §13). The SDK reads the graph, asks the strategy selected by `graph.layout.strategy` (default `nodera.graph-layout.layered`) with the host's `direction`/`spacing` and `scope: "all"`, and applies the answer through that use case; a strategy diagnostic becomes an SDK diagnostic and nothing is applied. Selecting `free` makes `arrange()` an honest no-op. Add-time placement keeps the deterministic grid rule of T1: a strategy arranges the whole graph, it never places a single node among positioned ones.

## Non-goals

- Any runtime, user-facing toggle for mode/direction/spacing: host configuration only (S4).
- Automatic re-layout of already positioned nodes, on add, on edge change, or on render (S4).
- Any React or React Flow import inside `packages/sdk` or inside the geometry package (S5).
- A new dependency before the L5 decision is recorded (S6).
- Execution/runtime semantics of any kind, and any change to the portable document contract: positions already exist and stay optional.
