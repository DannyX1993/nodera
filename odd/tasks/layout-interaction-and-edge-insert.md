# feature: layout-interaction-and-edge-insert

Layout-owned positions: anchored placement for new nodes, a host-selectable drag policy, inline edge insertion with a "+" affordance, and the phantom empty state.
Branch: continues on `feature/graph-layout-node-creation` (the previous feature is still unpushed; delivery decides whether it becomes its own PR). Four work units: placement anchors, drag policy, edge insertion, phantom state.

- S3: Layer contract carried over from `graph-layout-node-creation` (S5 there): geometry lives in a framework-agnostic package with no React/React Flow import; every position write goes through `@nodera/application` as **one** reversible history unit (AGENTS.md §12); nothing in `packages/sdk` imports React, React Flow, ui-react or a canvas; no external dependency is added (AGENTS.md §3).
- S4: Anchored placement (A). `addNode` accepts an explicit anchor (`after`, a node id). In `mode: "auto"` the new node lands in the next free slot **after the anchor** along the declared axis, stepping by the configured `spacing`; an occupied slot is skipped forward, never backward. Without an anchor the node lands after the graph's extent: the farthest occupied slot along the axis at its own row, stepped once more along the axis, first free slot from there. An empty graph still starts at the origin. The host decides the anchor — the palette passes the selected node when there is exactly one selection and nothing when there is none; the edge "+" passes the edge source. The SDK never reads UI selection itself.
- S5: Drag policy (B). `graph.layout.drag: "locked" | "snap-back"` (default `"locked"`) declares what a manual drag does when the layout owns the positions: `locked` makes the canvas refuse the drag, `snap-back` lets the node follow the pointer and returns it to its assigned position when the drag ends. The policy is host configuration with a runtime setter on `builder.graphLayout` (`setDragPolicy`/`dragPolicy`), it is reflected in the UI state so the canvas re-renders, and it never rewrites document positions by itself. A manual drag in `"free"` mode keeps today's behavior exactly.
- S6: Edge insertion (C). When the host enables it, the canvas renders one "+" affordance at the midpoint of every edge. Activating it opens the node-creation dialog (a `DialogDefinition`, customizable like any other dialog) and inserts the chosen definition **between** the edge's endpoints: one node plus two edges replacing the original edge, applied by an application use case as **one** all-or-nothing history unit (a failure writes nothing and emits nothing). The default button is overridable by the host through a renderer binding (component and icon), and the whole affordance can be turned off by configuration.
- S7: Phantom empty state (D). With the affordance enabled and the graph holding at most one node, the canvas draws a phantom node and a phantom edge carrying the "+", so a graph can be grown from scratch. The phantoms are presentation only: they never enter the document, never appear in `builder.graph.nodes()`, never emit events and never create history. They disappear as soon as the graph stops being empty.
- S8: Every unit pins its behavior through the public surface it owns (AGENTS.md §14), updates the docs that describe it (§17), and refuses invalid input with a structured diagnostic instead of guessing (§13).

- S18: Scoped arrangement (F). `builder.graph.arrange({ from })` applies the computed positions **only** to `from` and its descendants (reachable by following edges outward), leaving every other node where it is; the whole answer comes from the selected strategy, but only that subset is written, as one history unit. An unknown `from` is refused with a diagnostic and moves nothing. Without `from` the call keeps today's behaviour.
- S19: Downstream auto-arrangement (F). `graph.layout.arrangeOnChange: "never" | "downstream"` (default `"never"`) declares what a structural change does when the layout owns the positions: `"downstream"` means the builder arranges the changed node and its descendants automatically, in its own history unit, after `insertNode` and after a `connect`. An `addNode` of an unconnected node has nothing downstream, so it only takes its anchored slot. The setting is host configuration, never a user toggle, and `"never"` preserves the previous rule that only an explicit `Arrange` moves nodes.
- S20: Options panel (G). The example exposes every option the feature adds in one collapsible panel — strategy, direction, spacing, rank spacing, drag policy, connections, ports, `arrangeOnChange`, edge insertion, and the explicit actions (`Arrange`, reset/seed) — so a person can try each combination without editing code. The panel is the host's own HTML: nothing about it reaches the framework.
- S21: Successor placeholder (H). In `mode: "auto"` with the edge affordance enabled, every node with **no outgoing edge** gets a dashed phantom successor placed one step past it along the declared axis, joined by a dashed phantom edge carrying the "+". Activating it opens the node-creation dialog and appends the chosen type after that node and connects it, exactly like the near-empty phantom (S7). Phantoms stay presentation only: never in the document, the history or the events, and gone as soon as the node stops being a leaf.

- C — Edge insertion: the `insertNodeOnEdge` application unit, the SDK flow, the default "+" on edges with a renderer binding, dialog reuse, tests and docs.
- D — Phantom empty state: the phantom node and phantom edge with "+" in the canvas, tests and docs.
- F — Scoped arrangement: `arrange({ from })` (S18) and `arrangeOnChange` (S19).
- G — The example's options panel (S20).
- H — The successor placeholder for leaf nodes (S21).

## Non-goals

- Plugin-level contribution of the edge affordance: the renderer binding ships in C, the plugin packaging is a later phase (user: "en la siguiente fase").
- Any crossing minimization or edge routing (unchanged: `graph-layout-node-creation` S10 limitation).
- Automatic re-layout triggered by an edge change, an add or a render: recalculation stays an explicit host action (S4 of `graph-layout-node-creation`).
- Any runtime user toggle inside the framework's editor: the drag policy is host configuration, the example is the host.

- L6 (design note for F): the framework has no incremental ranker and does not need one. The expensive part of an arrangement is not the computation — the strategy ranks the whole graph in memory in one pass — it is what gets **written**: every position applied is document state and history. Scope therefore means "which positions are applied", not "which positions are computed": the SDK asks the strategy for the whole answer and writes only the subset of `from` and its descendants (outward reachability over the graph's edges, computed in the SDK). The auto policy stays host configuration, so the earlier rule "only an explicit Arrange moves nodes" still holds for a host that leaves it at `"never"`.
- L7 (interpretation for H, recorded so it can be corrected): "los pasos de la jerarquía donde aplique" is read as the nodes that end the hierarchy — those with no outgoing edge — because that is what the image shows (a single node, a dashed edge down, a dashed placeholder below) and it is the only place a successor is unambiguous.
