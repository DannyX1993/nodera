## Non-goals

- Plugin ecosystem: manifest validation, registry of manifests, dependency resolution, lifecycle states (load/activate/deactivate), cross-plugin conflict detection, example plugins — all Phase 7. Phase 6 ships the *plugin authoring contract* and synchronous installation only.
- Production readiness: accessibility audit, i18n, performance work, release automation, npm publishing, `exports` maps and bundling — Phase 8. Packages stay source-level (`main`/`types` → `./src/index.ts`, `tsc --noEmit`).
- Any new graph/domain capability: no grouping, no execution/runtime, no GGD contract change, no new event on `EventBus` (SDK-level events are composed above it).
- Any `@xyflow/react` import outside `packages/canvas-react-flow`; any React import inside `packages/sdk`.
- Vue/Angular adapters: the engine-agnostic port is designed for them, none is implemented.
- `packages/core`, `packages/plugin-api`, `packages/plugin-manager`, `packages/testing`, `packages/adapter-storage-*` stay untouched placeholders.

## Decisions

- D1: Two new packages, and the split is the phase's core idea.
  - `@nodera/sdk` — framework- and engine-agnostic. Owns `createBuilder`, the authoring translation layer, the composition root, all public APIs, and the **adapter port**. Imports no React, no `@xyflow/react`, no `@nodera/ui-react`, no `@nodera/canvas-react-flow` (enforced in `scripts/check-architecture.mjs`).
  - `@nodera/sdk-react` — the React binding and the first engine adapter. Owns `NoderaBuilderProvider`, `useBuilder`, `<NoderaEditor>`, and `createReactFlowAdapter()` (backed by `@nodera/ui-react` + `@nodera/canvas-react-flow`). A future engine/framework ships another binding; the SDK never changes.
  - Rationale: S9 + S10. A single package would either force React on headless consumers or leave the host hand-wiring `ui-react`/`canvas-react-flow`, which S1's result explicitly forbids.
- D2: The engine is selected through a declarative port, not an import. `BuilderAdapter` is `{ id, label, capabilities }` where capabilities describe what the engine can present (canvas, minimap, controls, zoom/pan, drag-and-drop, node/edge/port renderers, edge styles). `createBuilder({ adapter })` stores it and validates authored definitions against it, emitting `sdk.*` diagnostics for renderer slots the chosen engine cannot honour. The SDK never mounts anything: mounting is by definition framework code and lives in the binding.
- D3: Renderers cross the boundary as opaque `unknown` values. The SDK derives a stable renderer id from the definition `type` (`renderer` value is stored in `builder.renderers.nodes[id]`, the domain definition only carries the string id) and for property components from `<ownerType>.<propertyId>`. The SDK never inspects, types, or validates a renderer value; the binding validates that a bound value is a renderable component (`sdk.renderer-not-a-component`). This is the only way S3's `renderer: HttpRequestNodeRenderer` coexists with S9's "no React in the domain".
- D4: Public vocabulary follows FASE6 (S3/S7), not the internal packages. `type` maps to `NodeDefinition.id`/`EdgeDefinition.id`, `label` maps to `name`, `ports.inputs|outputs` map to `PortDeclaration[]` with `direction: "input"|"output"`, `properties[].options: string[]` maps to `PropertyOption[]` (`{ value, label }` with `label === value`). Materially different names are translated once, in `src/authoring/`, never leaked.
- D5: Edge `style` is split honestly. Keys that exist on `EdgeVisual` (`lineStyle`, `geometry`, `arrowStart`, `arrowEnd`, `color`, `animation`) map to it directly; every other key (`strokeWidth`, CSS-ish hints) is stored under `visual.metadata.style` so it survives and remains renderer-only. No new domain field, no silent loss.
- D6: `createBuilder` fails closed with `Result<Builder, readonly SdkIssue[]>`. Invalid authoring input, unsupported feature flags, unknown theme/layout ids and adapter incompatibilities are errors; non-fatal capability gaps are warnings collected in `builder.diagnostics`. Post-construction registrations return `Result<…, SdkError>`. `assertOk`/`assertValid` (S14) unwrap for linear host code.
- D7: `features` is validated, not decorated. Only implemented capabilities are accepted (`minimap`, `history`, `validation`); `grouping` and every unknown key produce `sdk.feature-unsupported` because silently ignoring a requested feature is a lie (AGENTS.md §13).
- D8: One additive application change: `EditorEngineOptions.domain?: NoderaDomain` (optional; default keeps `new NoderaDomain()`). Without it the builder cannot own the registries the host registered into, and `builder.createEditor()` cannot share them. No existing behaviour changes; existing editor tests must pass untouched (differential check).
- D9: The document API is a thin facade over Phase 2, with a format switch matching `application`'s existing `"json" | "yaml"` use cases plus the raw document object path. The FASE6 `GraphSerializer` object shape (S7) is offered as `builder.document.serializer(format)` returning `{ serialize, deserialize }`, satisfying the stated contract without replacing the free functions.
- D10: SDK-level events are composed above `EventBus`: `builder.events` delegates the 17 application events verbatim and adds the two SDK-owned ones (`plugin.registered`, `plugin.error`) because they describe builder composition, not graph editing. `EventBus` itself is unchanged (S11: existing tests untouched).
- D11: UICore `UiStateStore` is created by the builder (it is framework-agnostic) so `builder.ui` state is the single source the React binding consumes. `sdk-react` passes `builder.store` and `builder.registries.*` into `NoderaUiProvider` instead of letting it build defaults — otherwise `builder.registerPanel()` would have no effect.
- D12: `builder.editor` is exposed as an advanced escape hatch and is documented as such; the supported surface for graph mutation is `builder.graph`, a thin typed facade over the existing use cases (`Result` returns). No use case is reimplemented.
- D13: Package conventions follow Phase 5 (D12 there): `"type": "module"`, `main`/`types` → `./src/index.ts`, kebab-case files, colocated `*.test.ts(x)`, per-package `vitest.config.ts` (`jsdom` for `sdk-react`), `tsc --noEmit`. `sdk-react` reuses the phase-4/5 jsdom setup pattern.
- D14: `examples/phase6-demo` imports only the two SDK packages plus React/React DOM (host runtime), proving S1's result. It covers: register nodes/edges/properties through the SDK, theme switch, layout switch, panel tool, validation, JSON/YAML export, plugin `install()`, event subscription.
